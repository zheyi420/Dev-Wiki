# 暂存变更提交信息

只分析用户给出的目录里**已经暂存**的变更，起草一条可复制的提交信息。不执行 `git add`、`git commit`、`git push`，不改暂存区。

## 目录

用户消息中的路径就是目标目录。没有路径时只询问目录，然后停止。

1. 相对当前工作区根目录解析。工作区根目录不是 Git 仓库，不能当作目标。
2. 在该目录执行 `git rev-parse --show-toplevel`。失败就说明它不在 Git 仓库内并停止。
3. 之后的 Git 命令都在这个 toplevel 中执行，不要在工作区根目录执行。

用户给的是仓库子目录时，只分析该相对路径下的已暂存文件。同一仓库里暂存区还有此路径之外的文件时，用一句话指出它们没有进入本次提交信息。

## 读取

在仓库 toplevel 执行：

```text
git status --short
git diff --cached --stat -- <相对路径>
git diff --cached -- <相对路径>
git log -15 --format=%s
```

目标就是 toplevel 时，路径用 `.`。

已暂存变更为空时，直接说明并停止，不要编造提交信息。diff 很大时先看 `--stat`，再读决定意图的差异；锁文件和生成文件只说明有变动，不逐行复述。差异里出现口令、令牌、私钥或连接串时，提醒用户，提交信息中不要写入这些值。

## 提交信息

按 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/) 起草。用户当次的明确格式要求优先；否则若目标仓库自己的说明对提交信息有约定，遵循更近的仓库约定。没有额外约定时：

```text
<type>(<scope>): <说明>

- <正文第一行>
- <正文后续每一行>

<脚注>
```

- `type` 使用 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`。仓库近期提交稳定使用别的类型时，沿用那个类型。
- `scope` 是受影响模块的短名，小写。范围不明确就去掉括号，写成 `<type>: <说明>`。
- 说明使用简体中文，写变更的目的，不加句号，不逐文件罗列 diff。
- 第一行含 `type`、`scope`、冒号和空格，不超过 60 个字符。
- 原因从标题就能看懂时不要正文。有正文或脚注时，与标题之间空一行。
- 正文只有一行时直接写该句。正文有换行时，每一行都以 `- ` 开头，写成 Markdown 列表，不要写没有 `- ` 的续行。
- 破坏性变更在脚注写 `BREAKING CHANGE: `。
- 一次暂存包含多个互不相关的目的时，说明应拆开，并按目的分别给出提交信息。仍然不改暂存区。

## 输出

先用两三句说明这批暂存变更在做什么。然后只把提交信息放进一个代码块。不要执行提交。

```text
fix(flight): 修正列表筛选在进入详情后丢失

- 详情页重新取数时没有带上列表筛选条件
- 返回列表后原先的筛选状态被清空
```
