# 分诊问题报告

给一条 Slack 报告分类，并在它的来源讨论串里发一条有用的判定。只为明确的、新的 bug 建跟踪器工单。不要在这里复现或修复。

加载自动化提供的外部 Benny 配置。配置缺失、格式错误或不完整时，停下，不要发帖，也不要写跟踪器。

## 硬性安全规则

- 来源频道和根讨论串坐标不可变。
- 绝不在来源频道发根消息。
- 绝不发到别的频道、广播一条回复、发私信，或另开一条替代讨论串。
- 任何跟踪器写入之前，以及判定帖发出之前，都要预检来源父消息。
- 父消息缺失、已删除、不可访问或不确定时，停下，不做任何写入。
- 发一条有实质内容的判定。不要叙述进度。
- 协调者是唯一往 Slack 发帖的一方。
- 受托的 worker 只返回发现。它们必须是只读的，并且拿不到 Slack 凭据或写动作。
- 每条子 prompt 都必须禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage`，以及其他一切 Slack 写入。
- 如果 worker 隔离保证不了这些限制，就在协调者里做这件事。
- 绝不创建一条链不回来源讨论串的工单。
- 宁可没有工单，也不要猜测的或重复的工单。
- 对来源坐标应用 pstack 的 `principle-separate-before-serializing-shared-state`。
- 对最终判定应用 pstack 的 `principle-minimize-reader-load` 和 `unslop` skill。

## 1. 冻住来源坐标

列工作清单或委托之前：

1. 从触发里读 `source_channel_id`。
2. 要求它等于配置的来源频道。
3. 把 `SOURCE_THREAD_TS` 设成 `trigger.thread_ts`（若存在）。否则用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 非空。
5. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存成不可变的值。
6. 读讨论串，核实它的根消息恰好是这组坐标。
7. 取一条稳定的来源永久链接。

之后每一次来源读取和发帖都必须用这些存下来的值。绝不要用回复时间戳或运维讨论串时间戳替换它们。

## 2. 读完整份报告

做决定之前，先读根消息和当前回复。

记下：

- 报告人的原话
- 有的话，产品版本、应用构建、环境和平台
- 预期行为
- 观察到的行为
- 频率和触发条件
- 错误文本或栈特征
- 已有的工单、commit 或 PR 链接
- 任何明确说已经有人在修的陈述

检查每一份相关附件。

- 用足够看清的分辨率读截图。
- 看视频里把正确行为和坏掉行为分开的那段状态转换。
- 从日志、trace 和崩溃文本里读具体特征。
- 媒体需要专门审阅时，用一个只读的媒体 worker，问一个窄问题。worker 只返回发现。
- 附件读不了，就在判定里说出来。不要编造它显示了什么。

先用讨论串里已有的证据，再向报告人要更多。

## 3. 路由之前先追原因

选定负责人或目的地之前，先做一轮有界的源码和历史查看。从报告的动作追到观察到的结果。报告像回归，或碰到防御性代码时，用 pstack 的 `why` skill。

1. 从报告的动作到观察到的结果，找出可能的代码路径。
2. 检查看得见的症状属于这条代码路径，还是它下面的依赖。
3. 报告像回归时，检查最近的改动。
4. 检查已合并的 commit 或未合并的 PR 是否已经在处理同一症状。
5. 把确认的事实和假设分开。

这一轮不需要完整的根因。它必须强到足以避免把看得见的症状路由给错误的负责人。

仓库读不了时，不要猜代码负责人。继续做保守分类，并说明原因追溯不可用。

## 4. 分类

选一个类别。

### Bug

有东西违反了预期行为。例子包括错误输出、坏掉的状态、报错、崩溃、卡住、安静的空操作，或回归。

### 性能

报告描述了可测量的变慢、内存过量、耗电、卡顿，或其他资源问题。把它当 bug 处理，但保留测量和 profile。

### 功能请求

当前行为看起来是有意的，报告人想要另一种行为或另一种操作入口。

### 提问或反馈

报告在问某样东西怎么工作，表达了偏好但没有具体缺陷，或给出一般性反馈。

### 改道

原因追溯表明，另一个配置好的目的地拥有这个问题。

bug 和功能的分界不清楚时，不要建单。这一条判定可以问一个聚焦的问题，并使用 `other` 标记。

## 5. 应用配置好的路由

从 `routing.map_path` 读可选的路由图。

- 按已确认的产品区域、代码路径或错误特征来匹配。
- 原因追溯指向别处时，单靠看得见的症状不够。
- 没有路由匹配时，就说负责人不清楚。不要猜。
- 不要跨频道发帖。在来源讨论串里告诉报告人要把问题交到哪里。

负责人 ping 默认关闭。只有下面全部成立才允许 ping：

1. 路由图明确点名了负责人。
2. 配置允许这种 ping。
3. 这一项是需要负责人意见的功能请求，或者近期历史用强证据指出了可能的回归作者。
4. 负责人不是一个宽泛的值班组。

其他情况都不 ping。

## 6. 使用问题跟踪器适配器

跟踪器是适配器，不是某个必需的厂商。Linear 适配器是一个有效例子。GitHub Issues 适配器或其他跟踪器可以实现同一份契约。

配置的适配器必须提供：

- 按文本、状态、标签、来源 URL 和日期范围搜索工单
- 读取一条工单及其链接
- 用标题、正文、状态、标签和来源 URL 创建工单
- 更新已有工单，且不替换无关字段
- 添加来源链接和再次出现说明
- Slack 交接失败时，取消、关闭或删除这次运行创建的工单

某项必需操作不可用时，这次写入失败关闭。

在运行时解析配置的团队、项目、状态和标签。不要编造 ID，不要创建标签，不要指派负责人，也不要设置优先级，除非配置明确要求。

## 7. 去重

始终检查这条来源永久链接是否已经链到跟踪器工单或先前的分诊回复。如果是，不要发帖，也不要建重复项。

对 bug 和性能报告，用这些去搜跟踪器：

- 确切的错误或崩溃特征
- 产品区域
- 触发条件
- 症状
- 版本或日期窗口
- 可疑的回归 commit
- 来源永久链接

选一个结果：

- 有把握的重复：同一特征，或同一区域、同一触发条件和同一症状，或已确认的共同原因。
- 可能相关：共同原因说得通，但还没证实。
- 弱相似：相似只在表面上。
- 没有匹配。

对有把握的重复，用来源永久链接和一条短的再次出现说明更新已有工单。不要重新打开、改标签或重新指派，除非配置要求这么做。

对可能的匹配，在判定里按不确定链上它，并且什么都不建。

长期关闭的工单是一条回归线索，不会自动变成仍在处理的重复项。

## 8. 决定要不要创建

只有下面全部为真才创建：

1. 分类是 bug 或性能。
2. 行为明确是坏的。
3. 问题仍在，或者还不知道已经修好。
4. 去重没有找到有把握的，或说得通的、仍在处理的匹配。
5. 来源父消息和永久链接通过了预检。
6. 跟踪器的目标字段已经解析出来。
7. 判定帖失败时，适配器能够补偿。

功能请求、提问、反馈、改道、可能的重复、有把握的重复，或已经修好的问题，都绝不创建。

新工单必须自成一体：

- 点明区域和症状的朴素标题
- 报告人原话
- 预期行为和观察到的行为
- 版本和环境，或 `unknown`
- 触发条件和频率
- 来源讨论串永久链接
- 简短的原因追溯发现，假设要标明是假设
- 支持时内嵌截图或有代表性的视频帧
- 其余产物的链接
- 配置好的接入状态和标签

不要把猜出来的根因写进标题。

## 9. 发一条判定

重新做一次来源父消息预检。然后用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 恰好发一条回复。

`thread_ts` 为空时，绝不要调用来源频道的发帖动作。

回复保持简短：

- 开头就说结果。
- 有已有或新建的跟踪器工单时，链过去。
- 需要时提一句改道，或一个缺失的事实。
- 最多包含一次允许的负责人 ping。
- 以恰好一行标记结束。

标记契约：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只用配置好的标记字符串。复现自动化只在标记来自这条来源讨论串里、配置好的分诊身份时，才信任它。

发完之后，读同一条来源讨论串，核实判定出现在 `SOURCE_THREAD_TS` 下面。如果没有，绝不要在根上重试。

如果这次运行创建了跟踪器工单，而判定没有落地，就用适配器的补偿动作。核实工单已取消、已关闭或已删除。补偿无法核实时，只在自动化运行输出里报告失败。

## 10. 看一个跟进窗口

按配置的跟进窗口看来源讨论串，然后停下。

- 只回答直接问给分诊身份的问题。
- 安全时，把具体纠正写进跟踪器工单。
- 同一次运行里不要发出第二个标记。
- 不介入人与人的协调，也不介入旁支闲聊。
- 有人要求自动化停下时，提前停。

窗口最多延长一次。一条新报告应该另开一次运行。
