# 验证已有修复

未合并的 PR 或已合并的 commit 有可能修好这份报告时，用这个模式。

已有产物拥有这份修复。去验证它。不要改它，不要写竞争补丁，也不要另开一个 PR。

## 确认产物合格

必须有一份具体产物：

- 一个未合并的 PR，其中的代码改动针对这个症状
- 一个已合并的 PR
- 一个已合并的 commit，代码和意图都对得上

讨论串里的说法、跟踪器状态、分支名，或没有 PR 或 commit 的原因假设，都不够。

有多份产物时，选来源讨论串或跟踪器链到的那份。否则选和受影响代码最接近的一份，并说明原因。

## 保护工作区

仓库支持时，用隔离的 worktree 或其他干净检出。不要覆盖用户的改动。

记下：

- 基线修订
- 打过补丁的修订
- PR 或 commit 的 URL
- 两次运行共用的构建和环境输入

使用普通的 `github.com` PR 链接。

## 测量基线

对未合并的 PR，用它的基分支作为基线。

对已合并的修复，用修复正前面的那个修订，前提是它能构建，并且代表旧行为。

通过配置好的控制适配器：

1. 拉起基线应用。
2. 确认应用和环境是对的。
3. 用真实 UI 动作走报告里的路径。
4. 观察区分性症状。
5. 重置并再走一次。
6. 采集基线录屏、截图和状态检查。

症状没有在基线上出现两次，就没有基线。不要声称修复有效。

## 测量打过补丁的构建

用相同的环境和数据构建并运行这个 PR 或修复 commit。

1. 走同一条 UI 路径。
2. 重复两次。
3. 确认坏掉的状态已经消失。
4. 确认预期状态出现了。
5. 采集事后的录屏、截图，以及同一次状态检查。

不要停在编译或测试。事后结果必须来自一个正在运行的、打过补丁的应用。

## 结果

### 已确认

基线复现了两次，打过补丁的构建也两次都把它消掉了。

- 把运维状态标成已验证。
- 链到这份产物。
- 来源预检之后，在来源讨论串里发一条简短回复。
- 写上事前和事后的结果。
- 不要开 PR。

### 修复不够

症状在基线构建和打过补丁的构建上都出现。

- 把运维状态标成已复现但未修复。
- 链到这份产物，并说明它没有消掉症状。
- 如果这次运行还没用过，就发那条正常的、确认复现的来源更新。
- 不要开竞争的 PR。

### 无法下结论

基线没有复现，打过补丁的应用跑不起来，或证据没有显示区分性状态。

- 不要声称成功。
- 说明哪一半没能测到。
- 把结果留在运维讨论串或运行输出里。
- 除非有人直接提问、需要回答，否则来源讨论串里什么都不发。

## 清理

停下两份构建，按保留策略去掉临时配置档和采集，并把仓库恢复到之前的状态，不要丢掉用户的工作。
