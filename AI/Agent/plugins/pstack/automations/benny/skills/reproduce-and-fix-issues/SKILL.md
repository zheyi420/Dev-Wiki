# 复现并修复问题

在来源讨论串里等待可信的分诊标记。通过目标应用的真实 UI 复现确切症状。已有修复时先验证它。只有确认复现之后，才尝试一次有界修复。

加载自动化提供的外部 Benny 配置。配置、必需动作、控制适配器或填完的功能图缺失时，失败关闭。

## 硬性安全规则

- 做任何事之前，先冻住来源频道和根讨论串坐标。
- 绝不在来源频道发根消息。
- 每次在来源讨论串发帖之前，先预检来源父消息。
- 协调者是唯一往 Slack 发帖的一方。
- 受托的分析 worker 是只读的，只返回发现或媒体笔记。
- 修复阶段的代码 worker 只有在环境确凿地排除了 Slack 凭据和一切 Slack 写动作时才能改代码。否则由协调者来改。
- 每条子 prompt 都必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage`，以及其他一切 Slack 写入。
- 绝不要给子 agent Slack token、发帖指令、用于发帖的来源坐标，或向外报告的权限。
- 如果子 agent 必须有 Slack 写权限才能跑，就不要启动它。
- 工具 bot 是证据来源。除非有人明确把修复委托给它们，它们不拥有修复。
- 确切的区分性症状必须通过真实 UI 交互出现两次。
- 查看状态可以确认观察。它不得注入或强造症状。
- 没有确认的复现，就不要动手写修复。
- 已有的 PR 或 commit 会把这次运行切到验证模式。不要在它们上面另写。
- 使用 `github.com` PR 链接。
- 截图、录屏、日志和 token 不要进版本控制。
- 委托分析时用 pstack 的 `principle-guard-the-context-window`。
- 复现、修复和验证全程都用上 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 冻住来源坐标

列工作清单或委托之前：

1. 要求触发频道等于配置的来源频道。
2. 把 `SOURCE_THREAD_TS` 设成 `trigger.thread_ts`（若存在）。否则用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存成不可变的值。
5. 读来源讨论串，核实它的根消息就是这组坐标。
6. 取来源永久链接。

绝不要用回复时间戳、运维时间戳或状态消息时间戳替换这些值。

每次在来源频道发帖之前：

1. 按不可变坐标读讨论串。
2. 确认父消息存在、未被删除，并且仍属于来源频道。
3. 只用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再读一次讨论串，核实新消息是一条回复。

任一检查失败，就什么都不发。绝不要在根上重试，也不要改到备用频道。

## 2. 等待分诊契约

在配置的判定预算内看来源讨论串。等待期间保持沉默。

只有同时满足这些才接受判定：

- 作者匹配 `slack.triage_identity_user_id`。
- 它是 `SOURCE_THREAD_TS` 下的一条回复。
- 它恰好包含一个配置好的标记。

公开标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只对 `bug` 或 `performance` 继续。记下可选的跟踪器 URL。遇到 `other`、没有判定、不可信的作者、互相冲突的标记或超时，就安静停下。

这个标记取代私有 bot 身份和自由格式的判定匹配。

## 3. 应用归属和修复产物关卡

开始动手之前立刻重读讨论串。

### 有人明确在修

有人明确认领修复、给出具体实现计划，或让另一个 agent 去实现、打补丁、修复或开 PR 时，停下。

不要把这些当成修复归属：

- bot 在总结证据。
- 工具在查日志或工单。
- 有人让 bot 诊断、解释、检查或复现。
- bot 发了一条原因假设，但没答应去实现。

判断的是被请求的动作，不是有没有 bot。

### 已有修复产物

如果一个未合并的 PR 或已合并的 commit 有可能修好这条报告，就切到 `references/verify-existing-fix.md`。

产物可以来自讨论串、跟踪器工单、仓库历史或 PR 搜索。没有 commit 或 PR 的口头说法不是修复产物。

如果有人接手了这项工作但还没产出产物，就停下。不要跟他们抢。

## 4. 打开可选的运维讨论串

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现工作流里唯一允许的根帖。

把它的坐标存成 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不要和来源坐标搞混。

使用配置好的纯 Unicode 状态字符串。状态文字保持简短：

- 正在复现
- 未能复现
- 已阻塞
- 已复现
- 正在验证已有修复
- 正在尝试有界修复
- 已开 draft PR
- 修复没有落地

优先用配置好的 Cursor Slack 动作。只有用户为了补一个窄缺口才配置了 `BENNY_SLACK_BOT_TOKEN` 时才用它，例如编辑这一条状态消息。绝不要把 token 暴露给 worker。

如果没有配置运维频道，把详细状态留在自动化运行输出里。不要用来源频道的根消息代替。

## 5. 加载并检查控制适配器

读 `references/control-adapter.md` 和 `control.feature_map_path` 处已填完的图，然后调用 `control.skill_name` 指名的 skill。

找到和报告里的用户路径匹配的功能图小节。驱动应用之前先读它。没有小节覆盖这个功能时，把这次运行标成阻塞，不要编造路径或选择器。

要求全部七项能力：

1. 拉起配置好的目标应用和测试环境。
2. 导航到映射的功能，并演练它写明的状态。
3. 用点击、输入、按键、滚动、拖拽、调整大小或导航来驱动真实 UI。
4. 查看状态，但不改它。
5. 截图。
6. 开始和停止录屏。
7. 清理进程、会话、配置档和临时数据。

适配器不在，或任何必需能力缺失时，把运维状态标成阻塞并停下。不要把截图、单元测试、状态篡改或读源码假装成 UI 复现。

## 6. 研究这份报告

读完整的来源讨论串；有跟踪器工单时也读。

收集：

- 确切的动作路径
- 预期行为
- 观察到的行为
- 两者分叉的区分性状态
- 频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

检查截图和视频。有用时，用只读的并行 worker 看代码历史、测试想法、爆炸半径图和媒体。每个 worker 只拿一个窄问题，以及 Slack 写入禁令。

顺着这个动作追到仓库里。回归历史和防御性代码用 pstack 的 `why` skill。提出互相竞争的原因假设，并指出能把它们分开的证据。

## 7. 复现

通过控制适配器拉起目标应用。

动手之前确认应用、工作区、账号、数据集和功能状态都对。用稳定的应用标记。不要只靠窗口顺序或眼熟的标题。

用真实 UI 动作走报告里的路径。

在把它叫成已复现之前：

1. 说出正确的最终状态。
2. 说出坏掉的最终状态。
3. 走到它们分叉的地方。
4. 观察到坏掉的状态。
5. 重置足够的状态，让第二次尝试相互独立。
6. 重复同一条路径，再次观察到同一个坏掉的状态。
7. 可能时交叉核对一个真实的状态值。

预期中的对话框、加载状态或准备步骤不是 bug。要抓的是能把正确行为和坏掉行为分开的最终状态。

使用配置好的复现预算。预算内症状没有复现，就报告一个干净的 `Could not reproduce` 结果。环境给不出某项必需能力时，报告 `Blocked`，并写明缺了什么。

## 8. 采集并审阅证据

复现成功时：

- 把走到症状的整条路径录下来。
- 给坏掉的最终状态截一张图。
- 留一份短笔记，写下确切步骤和观察到的状态。
- 把产物放在配置好的临时产物目录里。

让一个只读的媒体审阅者回答一个问题：证据能不能一眼看出那个能区分对错的坏掉状态？

答案是否定或不确定，复现就还没确认。补更好的证据，或改用 `Could not reproduce`。

配置了运维讨论串时，详细证据只发在那里。来源更新保持简短。

## 9. 报告复现结果

先更新运维状态。

对 `Could not reproduce` 或 `Blocked`，来源讨论串里什么都不发。结果放在运维讨论串或运行输出里。

确认复现后，跑来源预检，最多主动发一条来源回复：

- 说明问题已复现。
- 有运维证据讨论串时链过去。
- 最多写三条短发现。
- 有跟踪器工单时链过去。
- 默认不要 ping 负责人。

只有配置的 Slack 动作能把证据留在同一条来源讨论串里，并且组织的保留策略允许时，才附上证据。

等待配置好的驳回窗口。如果有人指出准备或解读是错的，把复现纠正一次。窗口结束且没有有效驳回之前，不要开始修复阶段。

## 10. 验证已有修复

已有修复产物时，遵循 `references/verify-existing-fix.md`。

验证必须显示症状在基线上出现，在打过补丁的构建上消失。两条路径都要用真实 UI 走两次。

不要改已有修复，不要加竞争补丁，也不要开一份替代 PR。

## 11. 核定一次有界修复

只有下面全部成立才尝试修复：

- 结果是一次单纯的确认复现。
- 媒体审阅确认了坏掉的最终状态。
- 没有出现已有修复产物。
- 驳回窗口内没有人认领修复。
- 运行时证据指出了根因。
- 可能的改动落在配置的修复预算和仓库范围内。
- 控制适配器能跑基线构建和打过补丁的构建。

任一条件不成立，就保留复现报告，停下，不要开 PR。

关卡通过后，把运维状态更新为 `Attempting bounded fix`。

## 12. 追根因并实现

协调者拥有每一次 Slack 发帖、最终 diff 审阅、commit 和 PR。

只读 worker 可以：

- 追代码和历史
- 提议测试
- 画爆炸半径
- 审 diff
- 审媒体

它们不改代码、不执行外部写入、不发状态，也不拥有修复。

只有工具隔离从这个 worker 身上拿掉 Slack 凭据和一切 Slack 写动作时，这一阶段才可以委托一次范围很紧的代码修改。它的 prompt 仍必须带上明确的 Slack 写入禁令。协调者审这次修改，并运行或核实必需的测试。工具隔离不确定时，修改留在协调者这里。

用运行时证据确认机制。改代码之前先排除竞争假设。

用最小的、说得通的改动修根因。

- 有便宜的本地测试目标时，调用 pstack 的 `tdd` skill，并在修复之前写下失败的测试。
- 路径很贵、不清楚或集成很重时，写明为什么跳过 TDD。
- 无关的清理不要捎上。
- 改动超出配置的投入或风险预算时停下。

## 13. 证明修复有效

保留原来的基线证据。

在打过补丁的构建上：

1. 走同一条真实 UI 路径。
2. 重复两次。
3. 显示坏掉的状态已经消失。
4. 显示预期状态出现在它的位置上。
5. 补录一段之后的录屏并截图。
6. 交叉核对基线用过的同一个真实状态值。

编译、单元测试、代码审阅或看起来说得通的 diff，都不是事后证据。

跑聚焦测试，再对改动行为周围的爆炸半径做冒烟。覆盖改动可能影响到的附近状态、输入、权限、平台和失败路径。还有回归就停下，不要开 PR。

## 14. 开一份 draft PR

只有前后证据都齐了之后：

- 审最终 diff，查无关改动和密钥。
- 跑仓库要求的检查。
- 仓库工作流允许时，做小而有序的 commit。
- 开一份 draft PR。这个工作流绝不合并，也不部署。
- 用跟踪器支持的 PR 语法链到配置好的跟踪器工单。
- 使用配置好的公开 URL 形式，通常是 `https://github.com/{owner}/{repo}/pull/{number}`。
- 写上复现步骤、根因、测试结果、前后证据和爆炸半径检查。
- PR 正文和所有 Slack 更新都过一遍 pstack 的 `unslop` skill。

PR 创建失败时，不要声称成功。把 commit 或分支状态留在运行输出里，并把运维状态标成 `Fix did not land`。

成功时，把运维状态标成 `Draft pull request opened`，并在运维讨论串里发一条简短回复，带上 PR 链接。不要再创建第二条来源频道根消息，也不要再主动发来源回复。

## 15. 跟进和清理

在配置好的运维讨论串里看一个跟进窗口。

- 只用已经收集的证据回答直接的问题。
- 具体纠正推翻了准备时，应用这一次纠正，并把复现重跑一次。
- 不介入人的协调和旁支闲聊。
- 被要求停下时就停。

始终调用控制适配器的清理能力。产物只保留到配置的保留策略允许的时长。
