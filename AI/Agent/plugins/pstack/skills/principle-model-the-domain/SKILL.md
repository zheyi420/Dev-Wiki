# 为领域建模

把真实领域编码进数据结构，不要散落在条件分支里。一个贴合领域的结构会让非法状态无法表示，并删掉分支。写的时候选定它很便宜。事后再补，读起来像一次重构，于是被推迟。

可以选用：

- 用状态机，而不是散落的布尔值、阶段或生命周期检查。
- 用带类型的模型，而不是松散的参数或反复出现的形状假设。
- 用映射、注册表、查找表或可区分联合，而不是摊在多个文件里的分支。
- 用 reducer 或命令/事件模型，而不是临时的状态变更。
- 用围绕一整块领域知识组织的模块，而不是 load、validate、transform、save 这种序列。执行顺序不是所有权。
- 用一块小的模块边界，把重复的行为、所有权或不变量收拢起来。
- 访问模式需要时，用队列、缓存、索引、图、树或规范化集合。
- 其他任何贴合的结构。都不贴合时，先弄清代码绝不能允许什么、数据怎么被读取，再找正好编码这些约束的结构。

不要硬套抽象。如果当前形状已经清楚、局部、不太会长大，就用平淡的代码。对只增加间接层、却没有去掉分支、重复规则、非法状态或生命周期风险的抽象保持怀疑。

你跳过了这一步的迹象是：一个新功能又给现有的 if/else 链加了一条分支，或者又多了一个必须和第一个保持同步的布尔值。按时间拆分是另一个迹象。以阶段命名的模块，在各步骤里重复同一套领域规则。
