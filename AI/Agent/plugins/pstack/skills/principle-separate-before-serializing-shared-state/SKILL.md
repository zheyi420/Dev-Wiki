# 先拆开，再串行化共享状态

并发行动者可能共享可变状态时，先问他们是否需要同一个可变对象。不需要，就消掉共享。共享是真的时，用结构强制串行化：锁文件、顺序阶段、独占所有权。指示和约定不是并发控制。

**为什么：** 对共享状态的并发写会制造竞态。它们间歇出现，难复现，调试很贵。

**做法：**
1. **找出共享的可变状态**（两边都读又都写的文件、两边都推的分支、两边都定义又都消费的 API）。
2. **默认：消掉共享的写入目标。** 问：这些行动者需要一个权威对象，还是各自在发布独立的事实？给每个行动者自己拥有的文件、键、分支或状态目录，只在读取或报告的边界合并。两个 worker 各写自己的 `lastX` 字段，写进同一个 `state.json`，仍然是共享变更。`indexer-state.json` 加 `metrics-state.json` 不是。
3. **只有一个共享写入目标是真正的不变量时，才用结构串行化访问**（锁文件、顺序阶段、单写入者行动者，或原子的比较并交换）。把「我们需要一把锁」当成要检查的设计坏味道，不要当成默认答案。
