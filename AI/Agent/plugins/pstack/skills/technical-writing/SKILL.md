# 技术写作

写到一个疲倦的工程师第一遍就能看懂。四层都用上。

有三条规则压在这些层之上：

- **砍掉每个不干活的词。** 句子没有某个词也成立，这个词就走。「为了能够」收成「来」。「需要注意的是」什么都不是。
- **用短的、日常的词。** 用「用」，不用「利用」。用「帮助」，不用「促进」。用「做」，不用「进行」。长词必须用精确换回它的长度。
- **一条规则把句子写差了，就换个办法修这个句子，或随它去。** 一个句子每条规则都遵守，读起来却像机器写的，那它就失败了。

代码库就是词表。写真实的符号、文件、旗标或命令名，不要同义词，也不要一段对它的描述。

不要发明行话。用开发者会大声说出来的词：「移动」「删除」「一个只会减少的预算」，而不是「撤离」「棘轮」或「终局」。命名过的模式可以，只要文档第一次就说清它的意思。在你的回复里，提议一个新的冒犯词和它的替换，作为对 `unslop` 抽象隐喻规则的增补，附上 diff。不要编辑那个 skill。

## 变换节奏

一份文档可以每层都遵守，读起来仍然像机器写的：每句都削得很短，哪里都没有观点，没有一点具体的东西。

- 有意混合句子长度。短句落地一个点。长句带着条件或后果搬运一个事实。
- 一句一个想法，并不等于一句一个长度。把装着两个想法的句子拆开。留着装着一个想法的长句。
- 模式允许的地方，要有观点。解释要权衡取舍，所以说出你怎么看，而不是罗列利弊。参考保持干。
- 具体，不要无菌。不要「schema 改动可能引起问题」，要「列重命名会让构建失败」。

## 先选定模式（Diátaxis）

一份文档，一个模式。两个问题选定它：内容是告知行动（做）还是理解（想），以及它服务的是学习还是工作？

- 行动 + 学习：**教程**。
- 行动 + 工作：**操作指南**。
- 理解 + 工作：**参考**。
- 理解 + 学习：**解释**。

这只罗盘用在整份文档上，也用在一个句子上。

**教程：在做中学。** 学习者的成功是你的事，不是他们的。开头说学习者将要做出什么，而不是他们将要「学到」什么。每一步都产生一个看得见的结果，早，而且经常。告诉他们应该看到什么：预期输出、prompt 的变化、那一行日志。解释砍到一个从句加一条链接。保持具体。用「我们」来写，写成命令：「先做 x。现在做 y。」

**操作指南：通往一个目标的步骤。** 解决一个人已有的问题，而不是机器能执行的一个操作。假定对方胜任，跳过教学。只有行动：不要离题，不要背景，不要为完整而完整。那些改成链接。允许分叉和判断：「如果你想要 x，就做 y。」指南按任务来命名：「如何校准雷达阵列」，而不是「雷达阵列校准」。

**参考：供查阅的事实。** 只描述。不要指示，不要说服，不要观点。干、完整、确定。陈述事实、选项、限制和错误，不要含糊其辞。镜像被描述之物的结构，这样代码和文档可以一起导航。把材料放在读者预期的地方。能从代码生成的，就从代码生成。

**解释：理解，以及为什么。** 一个有边界的主题，离开产品也能读。每个标题都应该能在前面默默加上「关于……」。锚在一个真实的为什么问题上。给出上下文：设计决定、历史、约束、替代方案。观点只允许在这里，别处不行。

不要混模式：教程里不要参考表，参考里不要教程式的牵手，操作指南里不要争论。拆开，再链接。

## 把句子写给读者（Google 开发者风格）

- 用「你」对读者说话，用现在时。只有真正发生在以后的事才用「将」。
- 说清谁做什么：「编译器检查」，而不是「被检查」。只有行动者未知，或无关紧要时，被动才可以。
- 把指示写成命令：「点击提交。」事实平直地说。绝不要「应当被完成」。
- 条件放在指示前面：「要删除文档，点击删除。」
- 常见情形放前面。例外放后面。
- 听起来像一个懂行的朋友。不要时髦词，不要比喻，指示里不要「请」，规程里绝不要「简单地」「容易」或「很快」。如果它简单，读者就不会在这里。
- 不要预告（「我们很快将支持……」），也不要让连续的句子以同一个短语开头。
- 链接的文字要说出链接去向哪里：页面标题，或一句短描述。绝不要「点击这里」。优先在本页给一句上下文，而不是链出去。
- 标题承载的是要点，不只是话题（「先选定模式」，而不是「模式」）。用句子式大小写，不要每个词都大写。任务标题是不加修饰的动词短语（「创建实例」）。概念标题是名词短语。每页一个 h1，不要跳级。
- 序列用编号列表，其他用条目。用一个完整的句子引出列表。条目保持平行。
- 代码用代码字体。UI 元素用粗体。列举时保留最后一个逗号。丢掉「等」，并事先说清列表是部分的。

## 让陈述一次只承载一件事（STE 规则）

- 一句一条指示。别处也是一句一个想法。
- 拆开大约超过 20 个词的指示，以及其他大约超过 25 个词的句子。
- 警告或条件放在它所守卫的步骤之前：「如果热油碰到皮肤，就会受伤。」
- 留着「这个」和「一个」：「删除备份文件」有两种读法。「删除这个备份文件」只有一种。
- 给每个词一个意思、一份工作，然后守住。如果「检查」的意思是查看，就不要再用它表示约束。
- 每个动作选一个词，并坚持用它：用「开始」，不要这里「开始」、那里「发起」。
- 把规程写成直接命令，绝不要写成旁白，也绝不要用被动：「安装这个组件」，而不是「组件必须被安装」。
- 能不用 -ing 形式就不用。

## 不让句子有两种读法（Global English）

- 把「只」和「不」这类词放在它们所改变的那个词旁边：「只在增长时失败」和「失败只发生在增长时」说的不是一回事。
- 拆开长的名词串：「proto 导入预算检查脚本」变成「检查 proto 导入预算的脚本」。
- 让每个「它」「他们」和「这」指向一个显然的东西。拿不准时重复名词。绝不要用「这」或「这会」去指一整句。
- 不要省动词：「阶段 1 移动转换器，阶段 2 运行时」让阶段 2 没有动词。给它一个。
- 留着显示结构的小词，例如「确保开关是关的」里的那个连接。绝不要拿清晰去换字数。
- 系列里重复冠词，当它能防止误读时：「客户端和主机」是两个东西时，写成「这个客户端和这个主机」。
- 一个句子能按两种方式分组时，说清「和」或「或」连接的是哪些部分。「既……又」「要么……要么」和「如果……就」是免费的消歧器。
- 用句号，不用分号。把长破折号换成一个新句子。
- 括号里的文字要是一个完整的语法单位，或自成一句。绝不要用「(s)」构成复数。
- 不要斜杠：写「a、b，或两者」，不要写「a/b」或「and/or」。
- 每个东西到处只用一个名字。一份文档对同一件事说「闸门」「棘轮」和「预算检查」，就是在教三件事。没变的东西不要来回换叫法。
- 跳过习语、口语、拉丁缩写和隐喻。

## 语气与仓库细节

- 对这个 skill 碰到的每份文档应用 **unslop** skill。那个 skill 拥有注水模式目录：AI 词汇、填充、含糊其辞、格式痕迹。
- PR 描述和 commit 消息也是写作。除了 Diátaxis，每一层都适用于它们。PR 正文是一份简报，评审者不到一分钟就能读完。不要粘贴 swarm 日志、SHA 列表或指标表。链接它们。
- 产品 UI 字符串不是文档。那些用你们产品的文案指南。
- 代码片段用制表符缩进。写真实路径。每个计数或树的断言，在落地它的那个 commit 上为真，并附上重新生成它的命令。

## 改写示例

改前：

> proto 导入棘轮预算脚本参数的配置，经由 budget.json 完成。注意，重要的是要记住，带 --write 运行会把已提交的预算更新成反映当前计数，这只应当在降低它的时候做。如果超出，CI 失败。

改后：

> `budget.mjs` 从 `budget.json` 读取已提交的预算，并计数导入 proto 的文件。如果计数超出预算，CI 失败。只在要降低预算时运行 `budget.mjs --write`。
