# 爆炸半径

在一次改动交付之前，找出它会在别处弄坏什么。用于「X 的爆炸半径」、「这可能弄坏什么」，或评审一份你还不信任的小 diff。

和 `how`、`why` 配套。`how` 告诉你代码做什么。`why` 告诉你它为什么是这个形状。爆炸半径告诉你它会在别处弄坏什么。

列出调用方不是这份工作。agent 一秒就能 grep 到那些。这份工作是 grep 不会显示给你的那种破损。

## 不要相信你自己写的说明

一份听起来对的爆炸半径说明一文不值。它真假读起来都一样有说服力。所以不要把说明交回去。找出整件事所依靠的那一两个事实，用跑代码来证明它们。

### 你有多确定

对改动的安全性所依靠的每个事实，能便宜地往下走多远就走多远，并说明停在哪一步。

1. 你这么说。单独这一点一文不值。
2. 你指向了那一行。一个真实的 `file:line`，或库自己的源码。
3. 你表明坏情况不会发生。你把失败逐步走了一遍，它到不了。
4. 你跑了它。一段脚本或测试调用真实代码，你错了就会大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常是一段小脚本：导入应用交付的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读这次改动。diff，它添加、修改和删除的符号，以及它现在做得不一样的地方，包括 diff 没有写明的那部分。把 PR 和它的 commit 拉下来。
2. 找出它安全所依靠的那一个事实。大多数看起来有风险的改动，安全是因为一个单独的事实，例如「这次调用只丢掉已经死掉的缓存条目，其他什么都不做」。找到那个事实。它成立的话，大多数有风险的情况一次就排除了。把时间花在这里，不要花在一长串也许上。
3. 看 grep 停下来的地方。读你调用的那个库的源码，核对它钉住的版本和任何本地补丁。弄清事情什么时候跑：微任务、卸载和拆卸、Solid 和 React 的差别。跟上符号搜索会漏掉的东西：API 返回的 JSON、一个数据库列、一种线路格式、另一种语言在读同样的字节、一个功能开关、下游三跳的代码。
4. 对每个风险诚实。给它一个真实的发生可能，以及它发生时的真实代价。留下你确认了的风险。把你查过并排除的那些分开列。引用一个真实的 `file:line`。一次什么都找不到的搜索仍然是一个答案。绝不要编造调用方或 API。
5. 证明那一个事实。写一段跑真实代码的脚本或测试，跑它，把发生的事贴出来。
6. 改动又大又宽时，把它当成一次 `arena` 来跑。让不止一个模型回答同一个问题，再合并答案。不同的模型抓住不同的真实 bug。

## 交回什么

- **它做什么。** 变了什么，包括不明显的那部分。
- **它安全所依靠的那一个事实。** 把它说出来，说明你把它做到了哪一步，并给出证明。证明不了就写「未证明」。
- **风险。** 每一条点名它怎么坏、`file:line`、多可能、多糟，以及怎么检查。要紧的那些把证明贴出来。
- **已排除。** 你查了什么，以及为什么没问题。
- **合并之前。** 能抓住真实 bug 的最便宜测试或复现，包括你写的那段脚本。

经 `unslop` 来写，引用真实代码，放到任何公开的地方之前先去掉私人内容。

**回复：** 上面这份说明，那个安全事实要么已证明，要么标成未证明。
