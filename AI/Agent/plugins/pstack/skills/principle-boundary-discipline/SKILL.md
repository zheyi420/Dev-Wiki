# 边界纪律

把校验、类型收窄和错误处理放在系统边界上。无条件信任内部代码。业务逻辑活在纯函数里。外壳薄，而且机械。

**为什么：** 散落的校验吵、重复，还给出虚假的安全感。把逻辑留在框架接线之外，才能不靠框架来测它。

**模式：**
- **在边界上**（CLI 参数、配置文件、外部 API、网络协议）：校验，返回错误，防御性地处理。
- **在系统内部：** 带类型的数据，错误向外传，不再重新校验。信任类型。
- **跨过边界。** 暴露领域概念，而不是边界自己的私有表示。通用机制留在里面，专用策略放在边上。

**应用：**

校验和错误处理：
- 在解析时校验配置（那是边界），不要在业务逻辑里面校验
- 在边界把原始数据解析成领域类型
- 不要把传输、存储、框架或线路类型通过公共表面再导出
- 边界已经校验过时，调用链深处不要再做多余的空值检查

代码组织：
- 业务逻辑放在没有框架依赖的纯函数里
- 解析函数：从原始字节到带类型状态的纯变换
- 构造 prompt：结构化状态进去，字符串出来
- 评分和评估：从状态到结果的纯变换

**检验：**
- 「这份数据此刻是不是正在跨过系统边界？」如果不是，校验就是多余的。
- 「这能不能做成一个纯函数，让外壳只是调用它？」如果能，就抽出来。
