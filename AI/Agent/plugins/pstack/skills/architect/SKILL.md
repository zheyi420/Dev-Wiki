# Architect

用 `not implemented` 函数体和伪代码勾出类型、函数签名、类的形状和模块边界。综合多个模型的视角，再按选定的草图把代码填进去。

## 开始

动手之前先开一份待办，每个阶段一条。

1. 摸清
2. 草图
3. 对齐
4. 实现
5. 作废

## 阶段 A：把问题摸清

给新代码会碰到的每个系统建一个真实的心智模型。顺着相关子系统走一遍。点出一个文件名不算摸清。给每个子系统写一段架构说明。如果设计会重定所有权或分层，也对现有形状跑一遍 **why** skill，让理由变成约束，而不是猜测。

只有工作确实是从零开始、周围没有要接入的系统时，才跳过阶段 A。

## 阶段 B：草图

用设计草图这项任务和阶段 A 的摸底产物跑 **arena** skill。把 `references/runner-prompt.md` 当作每个 runner 的 prompt 传进去。

runner 取自 `architect runners` 那一行，这一行在 `pstack-models.mdc` 规则里，用来代替 `arena runners` 那一行。规则或那一行不存在时，用 `claude-fable-5-2-high`、`claude-opus-5-5-high-fast` 和 `gemini-4-carbon-high`。别名和被拒条目遵循 **arena** skill 阶段 A 的 runner 规则。

设计两遍。综合之前至少要有两个结构上不同的候选，即使第一个看起来已经够用。这是把 **exhaust-the-design-space** 原则 skill 落到具体。要整体形状的替代，不要同一个形状里的点状修补。

综合之前，用 [`references/design-red-flags.md`](references/design-red-flags.md) 筛每一个候选。假定下一个贡献者是一个 agent：它只看见自己打开的文件，抄最近的例子，走能编译的最短路径。把设计选成这样：从一个文件看起来对的改动，对整个仓库也是对的。

按接口深度比较可行的候选。优先选把更多复杂度藏在更小、更简单的公开表面后面的设计。接口够丰富时，可以把能力集中起来，调用链就短，能力也不会散到各层。

Arena 返回一份综合后的设计包。它的综合决定填进理由的「综合决定」一节。

## 阶段 C：对齐（可选）

默认拿综合后的设计直接进入实现。没有人工检查点。

只有调用者明确要求时才加入检查点：「/architect with checkpoint」、「停下来，实现之前先给我看」，或类似说法。这时把综合后的设计摆出来，停下来等签字。

无论哪条路，综合结果都可以单独作为一个 commit 交出去。这是 **foundational-thinking** 原则 skill 的「先搭脚手架」模式。填入过程中，有计划、有范围的破损可以接受，见 **outcome-oriented-execution** 原则 skill。实现之前如果要对设计施压，对综合后的草图跑 **interrogate** skill。

如果人反对这个形状（在检查点，或事后），把这当成阶段 A 的证据。重新摸清，重跑阶段 B，再写更多代码。

## 阶段 D：按草图实现

把 `not implemented` 函数体换成代码，把伪代码换成逻辑。综合后的草图就是契约。偏离它是要摆出来的信号，不要默默当成摩擦吸收掉。如果一个函数需要草图没预料到的参数，问清楚：是草图错了，需求漏了，还是实现做过头了。

## 阶段 E：架构错了就作废

如果实现不断产生草图吸收不了的摩擦，把草图扔掉。不要往错误设计上打补丁，见 **redesign-from-first-principles** 和 **fix-root-causes** 原则 skill。

信号是一种*模式*，不是单次出现。迹象：

- 同一种权宜之计的形状，在互不相关的代码里反复出现。
- 多个互不相关的边界情况，全都需要特例分支。
- 类型需要逃生口（`any`、强制转换、实践里总是被设置的可选字段）才能编译。
- 草图说状态不共享，却冒出「我们需要一把锁」的反射。
- 调用方必须知道抽象的内部规则才能用它。
- 实现里出现两处或更多独立的、同一形状的阶段 D 偏离。

用判断。几个边界情况定不了一个架构的罪。有些问题本身就复杂。数据里的复杂不是设计里的复杂。

作废时：

1. 理清已经建了什么。
2. 把新约束当成第一天就有的假设来重设计，见 redesign-from-first-principles。
3. 先减再加，见 **subtract-before-you-add** 原则 skill。新草图在长大之前，应当比旧的更小。
4. 回到阶段 B，重跑 arena。

## 产出

先写调用方的用法，类型草图从用法推出来。小改动用一个文件放新类型和签名。较大的工作用模块图加类型定义。理由跟草图一起交，形状按 `references/rationale-template.md`，包括用法草图和综合决定。
