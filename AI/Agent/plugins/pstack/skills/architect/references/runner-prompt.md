# Architect 的 runner prompt

编排者在阶段 B 把这个文件原样传给每一个并行候选 runner，并在周围填入可变输入：任务、阶段 A 的摸底产物、隔离的工作目录，以及写出产出的路径。工作目录在可用时是一个 git worktree，否则是草图目录下每个 runner 一个子目录。要紧的是候选之间彼此独立。

你在 architect 的并行探索里产出一份候选设计。先完整读 **architect** skill。那就是你所处的工作流。输出一份候选设计包：类型草图、函数签名、模块图，以及按 [`rationale-template.md`](rationale-template.md) 成形的散文理由。

遵守下面的纪律。编排者按这些轴比较候选，选出基底。

- 先写调用方的用法。先写 README 风格的用法和两三处真实调用点，再写类型，然后从用法推出类型草图。用法就是规格。两者必须一致，所以改草图去贴合用法，不要反过来。
- 先数据结构。核心类型对了，代码就变得显然。把每一种主导的访问模式在提出的结构里走一遍。如果答案是「以后再加 map / index / cache」，结构就是错的。
- 接口深度。比较公开表面后面藏着的能力，相对于这个表面有多大。优先选简单接口，把复杂度拉进被调用方，即使实现因此不那么简单。不要把传输类型或线路类型放在公开 API 上。在接口后面解析成领域类型。
- 共享状态：如果两个行动者可能都写，问「会发生什么？」如果答案不是「什么都不会」，默认改成每个行动者自己的状态，在读取边界合并，见 **separate-before-serializing-shared-state** 原则 skill。
- 让边界看得见。函数体用 `not implemented` 错误，难处理的逻辑用 `// TODO` 伪代码，文档注释写明意图和不变量。读者只读类型和签名，就应该能把数据从输入追到输出。
- 把不变量编进类型：难误用的类型 > 运行时检查 > 散文注释，见 **encode-lessons-in-structure** 原则 skill。
- 在边界校验，边界内信任类型，见 **boundary-discipline** 原则 skill。业务逻辑写成纯函数。外壳保持薄。
- 每个不变量一个事实来源。派生，不要同步。
- 适用处让状态转换幂等，见 **make-operations-idempotent** 原则 skill。问操作跑两次，或跑到一半崩溃，会发生什么。
- 短调用链。追流程如果需要超过三个文件，把层次压平，见 **laziness-protocol** 和 **minimize-reader-load** 原则 skill。

你是并行 runner 之一，各自用不同的模型。产出你这个模型能做出的最好设计。不要为了防着其他候选而把设计做保守。候选之间的差异，就是用来选基底和嫁接的信号。收敛到一个看起来安全的中间地带，探索就失败了。
