# 理由模板

跟类型草图一起交的散文。一页。标题用句首大写，不要套话。把斜体说明换成真实内容。

## 问题

*一段话。我们要做什么，以及现有系统或约束里的什么让形状并不显然。如果 [阶段 A](../SKILL.md#phase-a-ground-the-problem) 找出了设计必须遵守的约束（要互操作的现有类型、不能弄坏的调用方、越过我们边界的不变量），在这里点名，让读者看见你看见的同一组约束。*

## 用法（调用方视角）

*先写这个，再写类型草图。写出消费者会读的 README 或快速上手，再加上他们自己代码里两三处真实调用点。他们导入什么，调用什么，返回什么。[形状](#shape) 里的类型草图从这里推出来。两者必须一致。不一致时，改草图去贴合用法，不要反过来。调用方的体验就是规格。类型为它服务。*

## 形状

*推荐的架构。先数据结构。然后数据怎样流过这些签名。点名撑住设计的那些决定。说明哪些不变量编进了类型，校验住在哪里，以及系统故意不做的事。明确评判接口深度。说出公开表面藏起了什么复杂度，什么仍然暴露给调用方，以及为什么接口没有比需要的更大。每个决定引用背后的原则（例如 `per boundary-discipline`）。不要复述原则本身。*

## 综合决定

*由 [arena](../../arena/SKILL.md) 填。记录哪个候选成了基底、为什么，从其他每个候选改编了什么，以及拒绝了什么、为什么。*

## 接受的取舍

*所选形状做出的每个取舍一条。句式：「我们接受 X，换来 Y。」点名未来读者可能误当成疏忽的任何东西，包括看起来像过早优化或过早简化的东西。*

## 考虑过的替代方案

*必填。至少点名一个具体的替代形状，用一行说明它为什么落选。评判每个替代方案时看接口深度，不只看实现是否简单。点名它暴露给调用方的复杂度，以及它藏起来的复杂度。设计空间里真有竞争者时，这里放两三个替代方案。约束把答案逼到只剩一个时，一个就够，结论写成「这是唯一可行的形状，因为……」。不要列出同一形状的几种变体。这一节写所选形状考虑过并拒绝的设计替代，不是其他 runner 候选。*

## 未决问题与风险

*草图期间你注意到、需要人来权衡的事，以及实现开始前值得标出的风险。写成问题，不要写成断言，这样人的回答就是决议，而不是一条评论。*

## 下一步实现

*对着草图要先建的第一件事。一句话。综合之后（如果选了检查点，则在阶段 D 签字之后）你会立刻开始写的东西。*
