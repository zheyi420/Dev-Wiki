# 把 prompt 写明白

一条 prompt 说出意图，以及做完的检查。步骤由 playbook 提供，所以几句白话胜过一份规格。

## 写进去

- 目标。说清哪里错了，或用户要什么。
- 做完的检查。它能过能败。「弄好一点」和一段时长都不是检查。
- 要出示的证明。要真实的命令输出、流程的视频、存下的值，或一个前后数字。
- 用户已经知道的。一个症状、一步复现、一份日志或一条链接，能省掉 agent 一次搜索。
- 真实的约束。「先复现」「先别改任何代码」「行为零变化」「继续之前让我评审」，每一条都会改变 agent 做什么。

## 留在外面

- 怎么做。说要达成什么，给 agent 留出找到更好办法的余地。
- skill 或步骤的清单。手写的顺序会丢掉或打乱 playbook 保留的步骤。只有要覆盖某一个选择时，才点名一个 skill。
- 用户对原因的理论，直到 agent 重述了问题。一个说出来的猜测会收窄搜索。

## 先把上下文装上

- 对一份嘈杂的报告，让 agent 在做任何其他事之前，用自己的话、用白话重述底下的问题。误读会在任何代码存在之前露出来。
- 在新聊天里，用 `/recall` 这个主题上更早的工作。旧聊天里有新 agent 没有的上下文。
- 改不熟悉的代码之前，向 `/how` 要机制，向 `/why` 要原因。没有追过模型的 agent，会在第一个像样的位置修症状。
- 让 `/teach` 为一个选择做论证，例如「说服我它修的是原因，不是症状」。论证比摘要好检查。

## 先设计，再计划

- 不要接受第一个设计。要几个选项的原型，UI 附上截图或视频，再从证据里挑。
- 让原型回答未决问题。不要对抗式地评审一份抽象计划，因为评审者会发明出从不发生的风险。
- 对共享的包或 API，先要 README 或一篇教程，再回到代码。文档变成 agent 用来对照自己的目标。
- 只在设计定下来之后才要计划。计划的每一步都结束于一次检查。

## 短跟进

- 聊天里已经装着这项任务时，「做吧」「继续」「一直做到完」本身就是完整的 prompt。
- 主题变了就以「新任务」开头。否则模式会把这条消息当成下一步。

## 走开之前

- 说「我去睡了」或「我走开一下」，这样 agent 就不再问。
- 把做完写成每次迭代都能跑的检查，并把那个谓词交给 `/loop`。
- 要一个从已命名基座拉出的新 worktree。
- 预先回答 agent 会停下来问的事，例如「commit 之前别问我」。
- 要一份以后可以审计的决定日志。
- 给一个出口：「如果几个小时后你真的卡住了，停下，并写明为什么」。

## 一行纠偏

- 重述目标：「我说的目标是复现。我还没要求修复。」
- 点名原则：「用证明它能工作。给我看真实输出，不要构建日志。」
- 原则的名字能用，是因为 agent 已经读过这条规则。它的回复会点名这条规则改动了哪个决定。
