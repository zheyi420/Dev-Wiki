### 多阶段或多 PR 计划

**你拥有计划，不拥有代码。计划是一份清单，负责人逐框执行，操作者凭证据审计。** 计划就是交付物。不要实现。

1. 改动只是一两个文件，而且做法明显时，跳过计划。直接说出来，然后停下。
2. 动笔之前，按 `playbooks/prototype.md` 用原型把开放问题定下来。只问操作者那些没有任何一次运行能定的产品或偏好选择。
3. 写计划文件。开头写改动是什么、按落地顺序排列的 PR id，以及依赖图。依赖图说明哪些 PR 彼此独立、从主干拉分支，哪些要等哪些，以及每个 PR 可以碰的文件。然后每个 PR 一节。一个 PR 就是一处改动，带着它自己的证据（**sequence-verifiable-units** 原则 skill）。每一节都有复选框，分别对应它依赖什么、它编辑的文件、它构建的那一处改动、你看到的结果，以及它的验证。
4. 光有测试不算充分验证。一个 PR 只有单元、现场和性能三个框都勾上，才算验证过。每个现场框都用一个具体场景和一个通过谓词驱动真实界面。性能框写明指标、探针、先量到的主干基线，以及判定失败的那个数字。改了交互的 PR，合并前要等操作者评审。
5. 交回计划路径，然后停下。执行要等操作者明确放行才开始。

**回复：** 计划路径，各 PR 的 id 及其依赖、要过评审关的那一组，以及什么仍未证明。
