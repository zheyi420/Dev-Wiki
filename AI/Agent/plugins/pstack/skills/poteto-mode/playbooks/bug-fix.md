### 修 bug

**这件事归你。规划、审查、验证。** 调查和修复交给 subagent，你留在主位。按 Subagents 一节，为每个 subagent 按这项工作选定推理档位，以及快速或标准速度。

要科学。发出去的每一行，都能追溯到运行时证据。「也许有用」的双保险是假设，不是修复。它不发出去。证据推翻一个假设时，回退它所推动的改动。发出去的只有证据支持的最小改动，多的不要。

1. 你自己通过控制 skill（不可协商项），在对应的使用面上复现。哪怕调试或插桩规程写着要请用户复现，也一样。只有当你写明一个具体理由、说明控制面到不了目标，并且已经把它开到尽头之后，才去问用户。不能直接复现，就合成触发条件、收紧条件，或者加上插桩，直到它触发。
2. 用二分查找原因。先形成候选假设，再逐个排除，直到只剩一个。用受影响子系统的 trace，以及 **why** skill 里的回归历史，给这些假设播种。每一轮都取能切掉最多剩余问题空间的那一刀，拿到运行时证据，然后排除。程序状态看不清时，加上插桩或日志，在代码跑起来的时候读。不要猜。漫长或顽固的追查，用 Cursor 的 `/loop` 命令来推。在第 3 步的 architect/interrogate 扇出之前，用运行时证据确认存活下来的*机制*。
3. 规划修复。如果它跨过函数边界，先 `architect`。把实现交给一个 subagent，用你配置的修 bug 模型（默认 `claude-opus-5-5-xhigh`），范围要具体。
4. 在同一使用面上验证。原先的复现现在能通过。「无结论」或用错使用面不算通过。标出来。单测展示的是分支行为，证明不了 bug 不存在。
5. 把 commit 排好，让失败的复现落在 git 历史里、位于修复之前。bug 有一条便宜的本地测试路径时，失败测试先行的节奏见 **tdd** skill。测试会太贵、集成太重，或者不清楚时，跳过。
   这就是 **sequence-verifiable-units** 原则 skill 的标准做法：失败测试在前，修复叠在上面。
6. 跑 **开 PR**。

**回复：** 坏在哪里、根因、修复、你如何验证。把先失败、后通过的复现输出原样贴上。
