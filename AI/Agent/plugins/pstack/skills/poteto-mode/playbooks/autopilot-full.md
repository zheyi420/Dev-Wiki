### Autopilot-full

**判定归你，PR 不归你。每个 PR 从构建到合并由一个负责人带走。你的 swarm 没写过这些代码。在它证明即将落地的代码之前，什么都不能合并。**

一条判定覆盖一个补丁，一次绿色 CI 覆盖一个 head。第 4 步的完整 swarm 只跑一次，只有重大变更才再跑。`playbooks/shipping.md` 里的 patch-id 规则可以沿用一条通道的结果，每个新 head 都要有自己的绿色 CI。

1. **操作者的关卡优先。** 授权只覆盖队列里的条目，所以操作者标明归自己的条目，以及队列外的 PR，都停在可合并。要求把计划说出来，并不等于放行。
2. **每个 PR 派一个负责人，并把工作放在接替者找得到的地方。** 整个项目只解析一次托管平台。GitHub CLI（`gh`）是默认。若 `command -v origin` 成功，且 Origin 能解析这个仓库，每次 PR 操作都用 `origin pr`。否则留在 `gh`，并记下回退。绝不要求 Graphite（`gt`）。每个负责人都是一个 Cursor cloud agent：它构建，按 `playbooks/opening-a-pr.md` 开自己的 PR，在真实产物上证明变更，按 `playbooks/babysit.md` 看护到绿色，并在第 4 步和第 5 步都放行后合并。

   尽早开 PR，让 CI 和 bot 跟工作一起跑。代码要先清掉注水代码（`deslop` skill，来自 `cursor-team-kit` 插件（`/deslop`）），并过完 `/no-comments` 这一遍，才算就绪，所以完整 swarm 跑在已经做完的代码上。然后变基到当前主干，并在自证之前报告代码就绪的 head，这样验证跑在补丁即将落地的基线上。之后每个 head 都要报告。自证、CI 和看护都做完，再报可合并。修复轮留在这个基线上，除非会和主干冲突、弄坏 CI，或主干合入了已知的、改到相同文件的并发变更，因为每次变基都会重启 CI。在代码就绪那次推送之前，以及之后每一次需要验证者的推送之前，在已提交的 head 上跑仓库针对改动路径的检查。

   假定 VM 会死。启动后不久就推送，并按 **show-me-your-work** skill，在根 agent 的 store（路径见系统提示）里开一条决策轨迹。每完成一个单元就先推送，再开始下一个。谁派出 subagent，谁就在这个 store 里记下它的 id、状态，以及从同类过往运行得出的 stuck-after 时限，这样父级死掉时，根 agent 仍能探它。只强制推送你自己的分支，并把 `--force-with-lease` 钉在你上次推送或接手的那个 SHA 上。任何不是你做的推送，停下来，报告给根 agent。
3. **负责人从主干并行拉出，不要叠成 stack，** 这样每个 PR 各自落地。
4. **swarm 验证只做一次。** 完整 swarm 在代码就绪的 head 上跑一次。只有新行为、重新设计，或一大块新 diff，才再跑完整 swarm。变基、合并冲突的解决，或小修复，在新 head 上只派一个验证者。只改措辞，就不派。按 **swarm** skill，在代码就绪的 SHA 上扇出彼此独立的验证者。它们重跑关卡，通过控制 skill（例如 `control-ui` 或 `control-cli`，来自 `cursor-team-kit`）或指定的驱动器，在真实界面上现场证明承重行为，并审计 diff。没有现场通道，或者你还没审计可合并报告的回执，判定就不算干净，因为没有通道会相信自己没核过的说法。

   只拦截你能摆出来的问题：在这个 head 上有一次失败的运行，或 PR 把某行文档写错了。PR 的基线里已经有的问题，不论来自主干，还是 stack 里它下面的 PR，都不拦截，除非这个 PR 把问题抄进来，或新踩到它。只有用户会撞上的 bug、失败的关卡，或写错并已交付的文档，才拦截。其余都进后续。
5. **负责人只合并你验证过的内容，而且是在它即将落地的主干上测过的。** 只有绿色 CI，不足以授权合并。swarm 的各通道启动之后，合并准备变基到当前主干，报告新 head，并等待绿色 CI。

   合并前一刻，拉取主干，判断它的变更会不会影响这个补丁，因为主干每动一次就变基，永远做不完。即将落地的代码若从未测过，就变基并等待 CI，例如冲突、双方都改了同一文件，或这个 PR 要跑哪些检查变了。双方都改过的 lockfile 不必变基，条件是冻结安装在合并结果上能通过，而且本 PR 改动的包在那里的解析与 head 上一致。因为这次安装测的就是即将落地的 lockfile。安装失败，就必须靠变基把它修好。主干若改了补丁的调用方，或改了补丁所依赖的东西，例如它调用的代码或某个依赖版本，就在合并结果上跑补丁的检查，通过再合并。否则直接合并。若主干会逼出合并准备之后的第三次变基，就停住，报告给根 agent，由它给撞在一起的工作排顺序。
6. **跑根这一层。** 任何放宽关卡的事，例如上调预算或加一条允许名单，都要先有验证者的证明，再由你重新会签，因为想要绿色的是负责人。授权范围包含审批时，这次会签就是审批。负责人记下的那一笔指向你的会签，供通道核对。禁用的或软失败的检查一律撤下，因为它不再守住每一种情况。托管平台强制的审批，绝不代给，也绝不绕过，因为没有会签能覆盖它。

   操作者放行后，启用 `/loop 1h`，一直审计到没有剩下的委派工作，因为长跑会漂移，agent 会一声不响地卡住。每一轮都从主干重读这份 playbook，并补上漂移，例如没报告的 head、没记录的 agent，办法是让它的负责人记下来，因为漂移是记录上的缺口，不是卡死。它探到每个 agent，一直到叶子通道，并按副作用给每个下判断，因为状态文字和摘要能把卡住的子级藏起来。agent 出错、开不了回合，或过了自己的 stuck-after 时限仍没有新动静，就是卡住。到第一轮为止既没推送、也没写过一行轨迹的负责人，同样算卡住。正在等你或操作者的，不算卡住，要回复它。卡住的 agent 马上替换，不等它的停止落地。这一轮若为操作者改变了什么，结束时按 **ketchup** skill 把情况补上。什么都没变的一轮保持安静。
7. **操作者一喊停，立即停手。** 暂停以零写入指令传到每个负责人。各自报告停在何处，并保留简报，直到操作者解除。

**回复：** 按 **ketchup** skill 给操作者补上情况。覆盖每个 PR 的状态和判定、合并了什么、会签及原因、仍开着的操作者关卡、暂放的后续，并附上每个 PR 和各条轨迹的链接。
