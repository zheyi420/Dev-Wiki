### 调查

**答案归你。规划、分流、写下来。**

调查请求是只读的。它们产出带引用的解释或一条建议，不是代码改动。

1. 追踪问题所指的代码。动机类的问题，还要走 **why** skill。
2. 吞吐检查点保持一行：`throughput checkpoint: n/a, read-only investigation`。
3. 产出结果（概述 / 关键概念 / 如何工作 / 东西在哪里 / 易踩的坑）。如果请求是在几个方案之间做决定，就给一条建议，附一张权衡表。
4. 对回复使用 **unslop** skill。

不开 PR，不看护 PR，也不用 `architect`，除非这次调查是代码改动的前一步。若是如此，交还给用户，再分流到修 bug 或功能。

**回复：** 调查的产出。对「我们确定吗？」这类回答，写上你真正的判断和理由。前提错了就顶回去（见自主）。
