### 性能问题

**测量这条线归你。规划、审查、核对数字。** 每一处修复都要拴在一次测量上，不要用读源码代替测量。

1. 通过对应的控制 skill 抓一条基线 trace。用 **benchmark-checklist** skill 核验基线，之后的每个数字也一样。
2. 追踪代码，让假设落到实处。没有先跑过，就不要声称性能到了天花板。
   按顺序试这些性能口诀，最便宜的先试：
   1. 别做。结果没人用的工作，停掉，而不是把它做便宜。
   2. 做，但不要再做一次。
   3. 少做。
   4. 晚点做。
   5. 等他们不看的时候做。
   6. 并发做。
   7. 做得更便宜。

   靠前的某条口诀已经达标，就停。
3. 从 trace 规划修复。如果它跨过函数边界，先 `architect`。把实现交给一个 subagent，用你配置的性能问题模型（默认 `claude-opus-5-5-xhigh`）。按 Subagents 一节，为每个 subagent 按这项工作选定推理档位，以及快速或标准速度。审查 diff。抓一条修复后的 trace。
   用 **sequence-verifiable-units** 原则 skill，每一次尝试都先验证，再试下一次。
4. 解析并对比制品（JSON 转 sqlite，再 diff）。「无结论」或用错使用面不算通过。标出来。
5. 在 PR 里引用这次测量。
6. 跑 **开 PR**。

对着一个指标做持续改进，而不是一次性修复时，用 Hillclimb playbook（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后的数字、差值、制品路径。
