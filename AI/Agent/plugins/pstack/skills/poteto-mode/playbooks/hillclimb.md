### Hillclimb

**你守住指标，也守住实验的完整性。监督并评审。把一次次尝试委派出去。** 用于对着一个目标，持续、迭代地改进一件可度量的事。一次性的修复走修 bug 或性能问题。这里是那个循环。

核心纪律：一次改一处，测一次，留下或回退。不要把没测过的改动叠在一起，也不要凭读代码宣称胜利（**prove-it-works** 原则 skill）。

1. 选定指标之前，先把工作负载和架构落到实处。追踪目标，点名能推动结果的真实负载维度（数据规模、历史、状态、并发），并选一个能复现用户抱怨的案例。没有案例能复现，就先修好复现，不要拿去 hillclimb。然后钉死一个指标、怎样算更好，以及一条可检查的停止谓词：目标配上尝试次数的下限，这样提早撞上的运气不能结束这次运行（「比基线至少好 50%，且至少 10 轮」就是这个形状）。用户给了数字就用用户的，否则先谈定。
2. 建好测量 harness，证明它灵敏，然后冻结（**build-the-lever** 原则 skill）。跑一组对照的真实负载，确认目标案例能复现症状，而更容易的案例按预期分开。harness 若分不出它们，就改负载或指标。冻结前用 **benchmark-checklist** skill 审查 harness，并让它打印错误次数和完成的工作量。冻结之后，一条可重复的命令吐出指标，采样要足够压过噪声（取 N 次的中位数，不要单次运行）。任何改动之前，记下基线指标，以及回归关卡的一次绿色运行（那些必须继续通过的测试）。
3. 通过 **show-me-your-work** skill 打开决策日志。一份 `decision.tsv`，每次尝试一行：id、假设、改动、之前、之后、差值、测试、判定（留下或回退）、备注。每次尝试前先读。放在树外（gitignore）。
4. 每个假设都扎在第 1 步的架构模型上，所以它点名一个具体机制（「把 X 从启动路径上挪开，因为它挡住了首次绘制」），而不是「试试给什么加 memoize」。性能指标按性能问题 playbook（`playbooks/perf-issue.md`）第 2 步的性能口诀给假设排序。只借用顺序，不借用那一步的停止规则。
5. 循环，每轮一个假设：
   - 用你配置的 hillclimb 模型（默认 `claude-opus-5-5-xhigh-fast`），把改动交给 subagent，范围收紧。按 Subagents 一节，按这项工作为每个 subagent 选推理档位。监督并评审 diff，不要自己去敲（**guard-the-context-window** 原则 skill）。几个独立假设同时活着时，扇出到并行的 subagent，各自用自己的 worktree（**separate-before-serializing-shared-state** 原则 skill）。
   - 用冻结的 harness 测改前和改后，并跑回归关卡。
   - 只有指标的移动越过噪声，且关卡保持绿色，才接受。否则把改动整段回退。「也许有用」的微调不留。
   - 每个被接受的修复一个 commit，只暂存你改过的文件（`git add <files>`，绝不用 `-A`）。留下还是回退，这一行都要记。
   每一轮都在下一轮开始前做一次检查（**sequence-verifiable-units** 原则 skill）。运行若无人值守，只从自主运行 playbook（`playbooks/autonomous-run.md`）借用唤醒机制，不借用它的停止规则。
6. 推过第一个平台期。卡住时，连续被拒几次，就换一类、把擦边的合起来、重读源码，或在断定已经到顶之前试更猛的做法。正确和简单优先于那个数字。破坏行为的胜利要回退，守住数字的简化要留下（**laziness-protocol** 原则 skill）。
7. 谓词满足时停，或者剩下的想法太薄、不值那个代价时停。不要为了凑到谓词而放宽它，还有便宜又没试过的假设时也不要退出。卡住了就摆出来，不要空转。
8. 把接受的 commit 按落地顺序叠好，运行 **开 PR**。

**回复：** 指标和目标，从基线到最终的百分比差值，跑了多少轮（留下多少、回退多少），每个被接受的修复各一行，`decision.tsv` 的路径，以及再往前推的话你下一步最想试的主意。
