### 交付

**你对即将落地的东西负责。独立验证每个 PR，只落地从底部连起来的那段已验证运行，然后把手从 stack 上拿开。**

1. **先解析托管平台，再在落地前独立验证每个 PR。** GitHub CLI（`gh`）是默认。若 `command -v origin` 成功，且 Origin 能解析这个仓库，每次 PR 操作都用 `origin pr`。否则留在 `gh`，并记下回退。绝不要求 Graphite（`gt`）。每个 PR 一个验证者，各自是一个 Cursor cloud agent。它用匹配的控制 skill（例如 `control-ui` 或 `control-cli`，来自 `cursor-team-kit`），按用户会用的方式跑这次变更，拿父级对照 head，并在这个 PR 上贴出 `PASS`、`PASS+NOTES` 或 `FAIL`。只有没写这段代码的 agent 给出的判定才算，因为作者核的是自己打算建成的东西。绿色 CI 和表示批准的 bot 评审都不是判定，因为二者都不会按用户的方式跑这次变更。
2. **只落地从底部连成一段、且已验证的运行。** 从最低的未合并 PR 向上走，停在第一个没有 `PASS` 或 `PASS+NOTES` 的 PR。它下面的 PR 是这段运行，这段运行里最高的一个是天花板。已验证的 PR 若压在未验证的上面，就等待，因为它离不开下面的代码，无法落地。某个分支既不含也不需要那段代码，就可以挪到主干上，独自落地。它得先有一份新判定，因为旧判定是在那段下层代码还垫在下面时跑的，主干上并没有那段代码。
3. **再核对一次，判定是否仍在描述这份代码。** 一条判定覆盖一个补丁。链式变基会把上面每个 PR 挪到新的 SHA，同时不让任何检查失败。相信旧判定之前，先比较判定 SHA 处的 `git patch-id` 和当前 head。补丁若只差在测试、文档或 lint 配置，只要它跑过的东西在两个 SHA 上除噪声外构建相同，这条通道的结果就仍然成立。噪声是在判定 SHA 的两次构建之间也会出现的差异，或一枚嵌进去的 commit SHA。每种噪声连同涉及的文件一起报告，让读者能核对这次判断。变更本身仍要新的检查和一次评审，因为旧判定从没见过它。没有构建输出的通道，例如开发服务器，展示不了这一点，所以重跑它，并重新验证其他已经漂移的部分。
4. **自下而上落地，一次一个 PR。** 始终合并这段运行里最低的未合并 PR，用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`。在 Origin 上，普通命令还会合并你点名的那个之下的每个 PR。在 GitHub 上，基线仍是父分支的 PR 会并入那个分支，而不是主干。把 PR 读回来确认结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为合并队列仅仅把 PR 排上队时，合并命令也可能报成功，而请求的自动合并并不是一次合并。落地的 PR 读出来应是已合并，基线是主干，不是它的父分支。只在判定覆盖其当前 head 的 PR 上启用 `--auto`（Origin 的就绪即合并，或 GitHub 的自动合并），因为它会把任何一个就绪的 head 落地。一次合并落地后，把以已合并分支为基线的 PR 改目标到主干（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），把它的补丁移到合并结果上，并用 `--force-with-lease` 推送。判定覆盖的是补丁，不是它的 commit，所以由第 3 步的 patch-id 规则决定判定是否还在。检查通过，且判定仍然有效，就合并它。
5. **落地期间别动 stack。** 对分支或基线的唯一改动，是第 4 步移动下一个 PR，因为合并会落地那一刻分支和基线所持有的一切，有没有判定都一样。在 GitHub 上，在 `/loop` 之下用 `scripts/watch-pr/watch-pr --queued-stack` 监视这段运行，直到它在天花板处报告 `COMPLETE`。在 `--stack-prs` 里按自底向上的顺序传入这段运行的 PR 编号，每次重启监视器都传同一份列表。在 Origin 上，用 `origin pr view <pr> --checks` 重读当前 PR，每次 `origin pr checks <pr> --watch` 返回都重读，直到天花板读出来是已合并。父级合并时基线移到主干，这是预期，不是要修的损坏。合并卡住时，先弄清原因，再改任何东西。
6. **停在天花板。** 要延长这段运行就得有新判定，所以那是重新走一遍第 1 步。

**回复：** 已验证的那段运行及其天花板，每个 PR 的判定以及谁给出的，落地了什么、你如何确认，还有下一个缺口需要什么。
