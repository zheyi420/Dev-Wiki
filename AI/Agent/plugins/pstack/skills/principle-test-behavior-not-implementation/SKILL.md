# 测行为，不测实现

测试是对代码为它的用户做了什么的一个声明：调用方、最终用户，或另一个服务。行为是这些用户通过他们使用的界面能观察到的东西。这包括返回值、错误、他们能读回来的状态，以及对代码之外系统的影响，比如发出一个请求、写入一行，或发出一条消息。实现是他们观察不到的：私有辅助函数、内部调用顺序、中间数据，以及是哪个内部协作者做了这件事。

用两种想象中的编辑来评判每个测试：

- **打破行为。** 让代码返回错误的值、跳过一个效果，或把效果做两次。如果测试仍然通过，它什么也没证明。常见原因是：断言比契约更松、期望值由被测代码算出来、复述了一个从不跑读取它的代码的常量或 prompt 字符串，以及对测试自己造出来的数据做断言。
- **改内部实现。** 保持每一个可观察结果不变，重排底下的代码。如果测试现在失败了，它就被钉在实现上。每次重构都得改它，却仍然抓不到 bug。

留下能抓住第一种编辑、并且扛得住第二种的测试。其余的改写或删掉。要写出两者都满足的测试，就通过用户的界面用一个具体输入去驱动代码。期望值从需求推导，而不是从跑一次代码推导。断言契约承诺的东西，不多也不少。

做决定的是契约，不是断言的形状。当承诺是「空购物车绝不扣款」时，断言支付客户端没有被调用就是行为。再配一个确实发生扣款的用例，这样测试表明它看得见这次调用。被模拟的外部服务收到的载荷是行为，因为那个服务观察得到。对内部辅助函数的调用是实现，因为没有用户看得见它。没有记录匹配时，空列表是精确答案；测试只需要「有某个结果」时，它就是空洞的检查。一条精确的错误文案钉住了没有调用方会读的措辞。调用方用来分支的错误类型才是契约。

测试可以钉住一个不变量，而不是一次调用，比如必须同时存在于两张表里的键，或一次编译期类型检查。不变量就是行为。
