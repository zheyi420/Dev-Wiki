# Recall

**开始或恢复工作之前，你重建用户最近的工作上下文，并交回一份紧的胶囊：事情现在停在哪，下一步做什么。**

保持紧，贴着话题。只读范围内那些线程需要的东西，然后停下。

你的上下文住在两份记录里。你自己的聊天历史装着你做了什么、决定了什么。共享记录装着同一段代码在别的名字下发生的一切：用户一直在报告的症状、交出去又被回退的修复、生产里仍在报的错误。第二份记录住在版本控制、问题跟踪、聊天和 issue 频道、长文文档，以及错误追踪里。一个功能如果拖着一条很长的 bug 尾巴，故事大部分在那边，所以不要只从你的对话记录重建它。

对话记录在 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是工作区路径去掉开头的斜杠，并把每个「/」换成「-」（所以 `/Users/you/proj` 变成 `Users-you-proj`）。每一行是一条聊天消息。

1. 先分类，再路由。要恢复的是一次具体的先前聊天时，走 `session-pickup` playbook，不是这个。把习惯收成一份持久 skill 是 `automate-me`。一份给人读的工作摘要是另一项任务。Recall 在你行动之前，跨最近的聊天装入工作上下文。用户已经给了你一份完整的状态胶囊（路径、分支、这次改动）时，用它，跳过挖掘。
2. 搜索之前先锁住范围。钉住窗口（「最近」是一个真实区间，默认最近 7 天）、点了名的话题，以及工作区（默认当前这个。没人要求时，绝不读另一个项目的对话记录）。把范围说回去。绝不要悄悄把「全部」收成「最近 N 条」。
3. 在你的聊天历史上扇出。在一个快而便宜的模型上拉起并行 subagent，每个拿语料的一片。告诉每个 subagent：候选按真实修改时间排序（`ls -t`），绝不要按 UUID 名字。先 grep 话题，然后只读匹配的聊天，并且只读相关区域。跳过当前聊天，以及明显的噪声（subagent、eval 和测试聊天）。每个返回同一份模式，每次聊天一块：话题、用户的目标、决定、敞着的线索、挣扎和纠正，以及产物（PR、工单、分支），每一项引用聊天 UUID。只有一两段聊天时，跳过扇出，直接搜。原始对话记录留在 subagent 里。主线程只拿它们的发现。按 **poteto-mode** skill 的 Subagents 一节，为每个 subagent 按这项工作选定推理档位，以及快速或标准速度。
4. 话题点名了一个功能、文件、子系统、区域或 bug 时，扫一遍共享记录。这是默认，不是判断。 「我在 X 上的工作」也不能免。每个来源拉起一个调查 subagent，用 agent 模式，因为只读会拿掉 MCP，并问每个「当前状态是什么，试过什么又没站住，用户还在报告什么」。和聊天历史的挖掘并行跑。空结果也是发现。跳过不可用的 MCP，并说出来。把回来的东西折进简报。只有纯粹的活动回忆、没有点名目标时才跳过这一步（「这周我做了什么」），那时你自己的历史和现场状态就是全部答案。
5. 对照现场状态核实。把挖掘和扫查浮出来的 PR、分支和工单，用 `git` 和 `gh` 核对。答案取决于一个 agent 实际做了什么时（它跑了哪些工具、读了哪些文件、撞上哪些错误），读完整对话记录，不要只读裁过的本地副本。
6. 按下面的契约写简报。按线索分组。停在点名的话题上。

## 输出契约

先写胶囊，然后是线索状态，然后是问题，然后是下一步。更深的细节放在下面，或砍掉。

- **胶囊。** 最多 5 条。这份工作是什么，整体停在哪。
- **线索。** 每条一行，前面正好一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没有标签的线索还没做完，所以给它标上。
- **问题。** 最多 5 个，反复出现的那些。包括用户一直在报告的症状，以及交出去又被回退的任何修复，这样下一次尝试从上次失败的地方开始。
- **下一步。** 最有用的下一个动作，只要一个，要具体。

相邻的功能或工单留在外面，除非它挡住这一件。胶囊和线索的行数超出一屏时，先砍细节，再砍线索。简报经 **unslop** skill 来写，聊天发现按 UUID 引用，共享记录的发现按来源引用（PR 号、工单 ID、聊天永久链接、错误追踪里的 issue），公开输出之前先清掉私人上下文。

**回复：** 这份简报，按上面的契约。
