# 基础性思维

**结构性决定**保住选择余地。**代码级决定**保住简单。

**先定数据结构。** 写逻辑之前先把数据形状定对。早点定义核心类型，追每一条访问路径，选择匹配主路径的结构。

在代码层面，对结构做 DRY，不是对每一行。类型和数据模型应当收敛。三条相似的语句，仍然好过一个过早的抽象。明确好过取巧。测的是行为和边界情况，不是行数。

**并发推论。** 在参与者之间共享状态之前，问「如果另一个参与者同时改它会怎样？」如果答案不是「没事」，就隔离。

**先搭脚手架。** 如果某件事对后面每个阶段都有帮助，就先做它。问「后面每个阶段是不是都因为这件事已经存在而受益？」CI、lint、测试基础设施和共享类型是脚手架。按选择余地排序：先搭环境再做功能，先有测试再修。commit 保持小，并且只做一件事。

每一次增量都应当落地一个连贯的抽象，或者加深一个已经存在的抽象。不要把一项新能力摊到各个调用方上，变成特例协调。

减法在脚手架之前。先删掉死代码，再打基础。
