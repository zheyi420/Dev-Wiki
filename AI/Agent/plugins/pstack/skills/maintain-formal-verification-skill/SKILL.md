# 维护形式化验证 skill

形式化检查证明的是它所描述的东西的一条性质。代码变了、验证没变时，检查可以继续通过，而它描述的代码已经不存在了。那种通过是危险的情况，因为它看起来像一份证明。这个 skill 是验证 skill 的维护循环，对象是 `/create-formal-verification-skill` 生成的，或任何对着点名的代码跑模型检验器、证明器或代码级验证器的项目本地 skill。项目本地 skill 处理的是 agent 在使用那个 skill 时做出的改动。这个 skill 处理跳过了它的改动：合并、没用这个 skill 做的编辑，以及跨很多 commit 积起来的漂移。

## 结果

每次检查给一个结果，并说明是哪一个：

- **已同步**：自上次同步以来，没有改动改变检查所描述的东西，并且检查通过。
- **已更新**：代码变了，验证现在描述新代码，并且检查通过。
- **bug**：验证描述的是当前代码，而代码打破了这条性质。这是关于代码的一条发现。它不是漂移。
- **堵住**：检查没能重新对齐，或跑不起来。准确说明为什么。

一次检查可以同时是已更新和 bug：更新让验证重新描述代码，然后性质在它上面失败。

## 编辑范围

只编辑验证：模型、harness、性质文件，以及验证 skill 本身。一次运行期间绝不编辑产品代码，除非用户要求你这么做。性质在当前代码上失败时，不要削弱性质或模型去让它通过。报告这次失败。

## 一轮

1. **找出检查。** 验证 skill 没有固定名字，所以按它做什么来找：一份项目 skill，对着点名的代码跑模型检验器、证明器或其他验证器。读你找到的每一份，或用户点名的那一份。对每次检查，收集性质、它覆盖的代码、界限和假设、跑它的命令，以及上次确认它仍在描述代码的那个 commit。没有验证 skill 时，停下，并指向 `/create-formal-verification-skill`。skill 没有记录同步 commit 时，用上次改动验证文件的那个 commit，并说明你这么做了。

2. **按原样跑。** 改任何东西之前，把每次检查跑一次，并记下结果。这里的通过并不告诉你代码是对的。它告诉你旧的描述仍然成立。这里的失败可能是漂移，也可能是 bug。在第 5 步之前不要决定是哪一种。

3. **读覆盖代码的每一次改动。** 把覆盖的文件从同步 commit diff 到当前 commit，并读每条 commit 信息。也找挪走的代码：一个被改名、拆开或移到另一个文件的已覆盖函数，仍然是已覆盖代码。也找碰到检查所守卫的状态的新代码，例如一个写同样字段的新函数。对每次改动，判断它是下面哪一种：
   - **没有影响。** 改动没有改变验证所描述的任何东西，例如格式、注释，或验证没有覆盖的代码路径。对照模型或 harness 来核这一点，不要对照 commit 信息。
   - **验证不再描述代码。** 一个曾经是不可再分动作的步骤现在成了两个，加了或删了一个分支，一项检查挪了位置，一条新路径到达被守卫的状态，或一个值现在有了不同的范围。模型或 harness 必须改。
   - **承诺是有意改的。** 改动改变了代码承诺的东西，而且改动里的证据说明这是有意的：文档注释、测试、变更日志，或 commit 信息。性质必须改，而且你必须引用那份证据。
   - **承诺可能被打破了。** 代码变了，没有任何证据说承诺变了。随之而来的失败当成 bug 候选。

4. **从代码更新，不要从结果更新。** 改模型或 harness，让每个变了的部分再次指向评审者打得开的代码，并让代码里一个不可再分的步骤在验证里仍是一个步骤。重跑之前先根据代码写下更新，不要按什么能让检查通过来塑造它。只有承诺是有意改的，才改性质。写下旧措辞、新措辞和证据。界限保持不变，除非这次改动让它们错了。你必须缩小一个界限时，在报告里说明。

5. **重跑，并判定每个结果。**
   - **通过：** 检查现在可以通过，而描述可能已经失去失败的能力。按性质所守卫的方式打破新代码，例如去掉一项新检查，或重排一个新步骤，并确认检查能抓住它。然后丢掉这次打破。
   - **失败：** 把反例对着真实代码逐步重放。某一步在代码里不可能发生时，验证是错的。修验证，并说明错在哪。每一步都可能发生时，它是一个 bug。点名引入它的 commit，用代码自己的话把反例讲成一串步骤，并用一句话说明伤害。对着真实代码的一个便宜测试或复现能显示这个 bug 时，把它作为证据加进报告。不要把它 commit 进产品代码。

6. **更新验证 skill。** 更新每次检查覆盖的代码、命令、界限、假设和同步 commit。把同步 commit 设成你核对过的那个 commit。堵住的检查不要移动同步 commit，并在报告里说明。然后按下一个 agent 会做的那样把验证 skill 走一遍，这样你知道它的步骤仍然能跑。

## 报告

对每次检查告诉用户：

- 结果，以及你读过的 commit；
- 验证里变了什么、为什么，每次改动一个短理由：代码变了形状，或承诺是有意改的（带上证据）；
- 重跑结果，以及你用来表明更新后的检查仍然能失败的那次打破；
- 每个 bug，用平白的话：反例是代码用语里的步骤、伤害，以及引入它的 commit；
- 验证仍然不覆盖什么，包括它应该覆盖却没有覆盖的新代码。

直说哪些失败是验证里的漂移，哪些是代码里的 bug。一次检查在你更新之前通过、更新之后失败时，说明旧的通过是在一份过时的描述上。

把验证更新放在它们自己的一次改动里，和任何产品修复分开。
