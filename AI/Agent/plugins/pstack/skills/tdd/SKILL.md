# TDD 修 bug

修一个有清楚、便宜测试路径的 bug 时，在改生产代码之前，先让坏掉的行为可以执行。目标是一个聚焦的回归测试：修复前失败，修复后通过。

不切实际时不要硬写测试。如果现有测试需要大范围的 harness 搭建、脆弱的 mock、缓慢的端到端基础设施、只有生产环境才有的状态、含糊的复现步骤，或大片无关的夹具变动，就不要加新测试，改用最接近的有用验证。

## 流程

1. **理解这个 bug。** 找出预期行为、当前行为、受影响的路径，以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用这段代码路径上已经在用的、最接近的单元、组件、集成或回归测试。如果没有显然可行的测试路径，不要为了满足流程从零造一个。
3. **先写失败的测试。** 加上最小的、能抓住这个 bug 的聚焦测试。测试应当编码预期行为，而不是照搬当前实现。
4. **修复之前先跑这个新测试。** 确认它因为预期的原因失败。如果它通过了，或因为无关原因失败，先改测试或复现，再改实现。
5. **修 bug。** 做满足预期行为的最小生产改动，同时保住附近的契约。
6. **重跑回归测试。** 确认测试现在通过。

## 失败测试不切实际时

改用最接近的可执行回归检查：一段针对性脚本、手工复现命令、浏览器自动化、快照比较、日志断言，或聚焦的集成检查。

宁可没有新测试，也不要一个坏测试。坏测试是：主要在测 mock、编码了当前实现细节、依赖时序或无关的全局状态、为一个小修复需要昂贵的基础设施，或者证明修复之后马上就会被删掉。

## 边界

- 不要只为了迁就一个错误实现去改测试。
- 不要削弱已有断言，除非预期行为确实变了，而且理由清楚。
- 回归测试聚焦在这个 bug 上。避免大片夹具变动或无关的覆盖扩张。
- 如果 bug 是不稳定的，尽可能让测试确定，并写明被锁住的信号。
- 如果 bug 暴露的是更大的一类失败，先落地这条聚焦的回归路径，再考虑额外的同类覆盖。

## 最终回复

报告证据，而不只是结果：

- 点名修复前失败的测试或可执行检查，以及它产生的失败。
- 点名修复后通过的测试运行，以及附近做过的验证。
- 如果没法展示修复前失败的证据，说明为什么，并描述改用的最接近的回归检查。
